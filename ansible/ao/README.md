# Automation Orchestrator workflows as code

**Source of truth for the six AAC AO workflows**, exported from the lab AO (`ao-automation-orchestrator`, namespace `automation-orchestrator`) on 2026-10-08. Until this directory existed the only copy was the AO database on the lab host.

`workflows/<slug>.json` is the AO `workflow_definition` as the API returns it (`GET /api/v1/workflows/<id>/versions/<n>`), with the two post-export edits listed under `provenance.changes_since_export` in the manifest. `components.yml` is the dependency manifest, **generated by `scripts/ao_components.py`**: what each workflow needs to exist before it can be imported anywhere. Lab UUIDs inside the JSON (AO integration, AO credential, LLM model) are environment-specific; `components.yml` → `environment_ids` maps every one of them to its name and type, so a loader can replace each ID deterministically — resolving by **name** at import time, the way `sales.demos` does (`ao_workflows.yml` + `tasks/ao_workflow_apply.yml`). The two LLM model IDs still need their model names filled in (`name: null`; `GET /api/v1/llm-models` on the lab AO lists them) — note that Mythos deliberately uses **two different models under one integration**, so a loader keyed only by integration name would collapse them.

## Node types a loader must carry

`aap_job_template`, `aap_workflow_job_template`, `agentic` (with `response_schema`, `integration_connections`), `http_request`, `switch` (cases on `${node.body.result.route}`), `approval`, `converge` (Mythos), and a `manual_trigger` with an `input_schema`. ## Changed since the export

Two definitions were corrected in git after the 2026-10-08 export, so the lab AO holds older versions until they are re-imported (or the same edit is made on the canvas):

- **Mythos Patch** — `final_gate` now passes each validation gate's `body.result.flags` into `input.assessments.<dim>.flags`. The composed routing policy carries those into `decision.flags`; the lab v18 body omitted them, so low-confidence and invalid-evidence flags were silently dropped.
- **TEST call workflow-template** — `call_wf.extra_vars` passes `target_host`, the variable `AAC_GoldenImage_Enforcement` and the Golden Image templates consume (the governed drift workflow already did). It passed `target_hostname`, so the requested host never reached the templates.

## Regenerating

Log in to AO (`POST /api/v1/auth/login`), `GET /api/v1/workflows?limit=100`, then for each AAC workflow `GET /api/v1/workflows/<id>/versions/<current_version>` and write `.workflow_definition` (Python `json.dumps(indent=2, ensure_ascii=False)` reproduces the stored formatting). Keep the slug from the workflow name, update `provenance.lab_versions` in `components.yml`, then:

```bash
python3 scripts/ao_components.py          # rewrite components.yml from the JSON
python3 scripts/ao_components.py --check  # CI-style: exit 1 if the manifest is stale
```

The script preserves the hand-maintained `provenance` block and the id → name/type fields under `environment_ids`, and rewrites everything else. A UUID the JSON uses that has no entry yet appears with `name: null`.

## Security posture of the agentic nodes

A security review of these exports flagged the agentic nodes for **excessive
agency**, correctly. The exports carry seven agentic nodes across four
workflows. Five attach the AAP MCP server with `tool_selection_strategy: ALL`;
five read `set_stats` artifacts that jobs published from the managed host
(drift details, file names, package lists); **three do both**, and those three
are the prompt-injection path: host-controlled text reaching a model that holds
AAP tools. With a write-enabled MCP server the ceiling is "a crafted drift
message gets the triage agent to launch a job".

| Workflow | Agentic node | MCP tools | Reads host-published facts |
|---|---|---|---|
| AMI Golden Meter | AI Bad-Actor & Criticality Triage | ALL | no (trigger inputs only) |
| Golden Image | AI Drift Triage | ALL | **yes** (`identify`) |
| Mythos Patch | Agent: Blast Radius | ALL | **yes** (`identify`) |
| Mythos Patch | Agent: Patch Known-State | none | yes (`identify`) |
| Mythos Patch | Agent: Environment & Readiness | ALL | no |
| Mythos Patch | Agent: Technical Debt | none | yes (`identify`) |
| Tanium Comparison | AI Drift Triage | ALL | **yes** (`check`, `state_query`) |

What bounds it, and what any environment loading these must keep:

1. **The agent's output is an input to the policy, not the route.** Every agent
   result is posted to `opa-routing` and the switch acts on the policy's
   verdict. How much weight the recommendation carries differs per workflow,
   and that is what to read before trusting a flow:
   - *Golden Image* (`drift_routing`) and *Tanium* (`tanium_drift_routing`):
     the route is computed from the job facts alone; the recommendation is
     only recorded as `agent_recommended` / `overrode_agent`.
   - *AMI* (`ami_routing`): the recommendation can only make remediation
     *less* permissive. `auto` needs valid facts, an authorized change, a
     non-critical asset **and** an `auto_remediate` recommendation. The one
     agent-driven action is escalation: `bad_actor_suspected: true` routes to
     the CIP-008 incident job without approval. Injection can raise an
     incident; it cannot buy a silent remediation.
   - *Mythos* (routing policies not included in this release): the four agents' scores
     **are** the numbers the routing bands are computed from. The scoring policy
     clamps ranges and fails closed on malformed output; it does not second-guess
     a plausible score. This is the workflow where agent output most directly
     shapes the route.
2. **Human approval gates one branch, not all remediation.** In AMI, Golden
   Image, Tanium and Mythos the `auto` / `auto_remediate` verdict goes straight
   to rollback, enforcement or the patch lifecycle; only the `approve*` verdict
   passes through an approval node. The safety of the auto branch rests on the
   OPA verdict (and, for Mythos, on the clamped scores), not on a person.
3. **The MCP connection the agentic nodes attach must be read-only.** State
   the server's write posture per environment, never default it; attach a
   read-only server to these nodes even where a write-enabled one exists for
   people.
4. **Nodes that need no tools attach none; nodes that need few get few.** Two
   of the Mythos agents already run without an MCP connection. Blast Radius's
   prompt names seven read-only inventory tools but its connection is still
   `ALL`; narrow it to those seven.

`components.yml` carries `agentic_tool_access` for every agentic node
(`mcp_tools`, `reads_host_published_facts`, `host_fact_sources`,
`output_feeds_policy`) and a `security_note` on every MCP-attached workflow.
Both are **derived by `scripts/ao_components.py`** from the workflow JSON, so
they survive regeneration and `--check` fails if they drift.
