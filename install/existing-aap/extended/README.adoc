= AAC on Existing AAP — Production-Oriented Install Guide
:toc: left
:toclevels: 3
:sectanchors:
:sectnums:

*Version:* 2.1 — co-authored with Claude (Anthropic)

Estimated time: 2 to 4 hours for a careful first install.

== What you get

- OPA containers (`opa-security`, `opa-compliance`, `opa-ot`)
- REGO policies loaded from the `policies/` submodule
- A *dedicated* AAC PostgreSQL database
- Grafana dashboards
- An AAP project + job templates
- A controller execution environment entry for *AAC Compliance EE* (you build the image and point CaC at your registry)

== Architecture recommendation

Prefer a dedicated AAC host to provide clear blast radius, capacity, and naming. Do not risk AAP data or container names. The EDA and MCP configurations are optional for a first production cut.

All AAC containers (OPA, PostgreSQL, Grafana) run *rootless* as the `compliance` service account, managed by user-level Podman Quadlets. AAP reaches the host over SSH as `compliance` and talks to the services over HTTP and PostgreSQL.

== Prerequisites

- AAP *2.5.5* or later
- RHEL 9.5 or later, registered with Red Hat
- Outbound HTTPS to GitHub, console.redhat.com, and registry.redhat.io
- Firewall capacity for the ports opened by `scripts/aac-host-prereq.sh`: OPA (8181, 8182, 8183), Grafana (3000), reports viewer (8080), services (5000–5004), and *optionally* PostgreSQL (5432; skip with `--skip-pg-firewall` when AAP reaches the database on a private path)

== AAC host setup

The *installation user* in this guide is the `compliance` service account created in the first step. Every step after it runs as `compliance` unless it says *root*.

=== Prepare the host (root)

As root, install git, take a temporary clone to get the scripts, and run the prerequisite script. It creates the `compliance` account (passwordless sudo, systemd linger), installs packages, opens the firewall ports, creates the podman volumes, upgrades the system, and reboots.

[source,bash]
----
dnf install -y git
git clone https://github.com/Ansible-Automated-Compliance/aac.git /root/aac-bootstrap
/root/aac-bootstrap/install/existing-aap/extended/scripts/aac-host-prereq.sh \
  --skip-ansible-deps --upgrade --reboot
----

`--skip-ansible-deps` is required here: the collections are installed by `compliance` from its own clone in the next step. Set a password for the account with `passwd compliance` (or pass `--password`). Use `--help` to see all options. After the reboot you can delete `/root/aac-bootstrap`.

=== Clone your fork (compliance)

From GitHub, fork https://github.com/Ansible-Automated-Compliance/aac.git. Log in to the AAC host as `compliance` over SSH (not `su`, so the user systemd session is available), clone your fork, initialize the submodule, and create a branch for your installation work:

[source,bash]
----
git clone https://github.com/<your-github-username>/aac.git
cd aac
git submodule update --init --recursive
git checkout -b installation-work
cd install/existing-aap/extended/
----

*All remaining commands in this guide run from `install/existing-aap/extended/`.*

Install the Python and collection dependencies used by the bootstrap playbooks:

[source,bash]
----
pip3 install --user psycopg2-binary
ansible-galaxy collection install -r playbooks/requirements.yml
----

NOTE: Some collections in `playbooks/requirements.yml` are certified content. Configure `ansible.cfg` with your console.redhat.com token or your Private Automation Hub before running `ansible-galaxy`.

=== Log in to registry.redhat.io (compliance)

[source,bash]
----
podman login registry.redhat.io
----

NOTE: Rootless podman keeps this login under `/run/user/<uid>`, which is cleared on reboot. Images already pulled keep working; log in again before pulling new or updated images.

[[aac-host-ssh]]
=== AAC host SSH key (AAP → compliance)

Job templates that act on the AAC host use the *AAC Host (SSH)* credential: AAP connects as `compliance` with the private key stored in `playbooks/vars/secrets.yml` (`aac_host_ssh_private_key`). The matching public key must be in `~compliance/.ssh/authorized_keys`.

Generate a dedicated ed25519 key pair:

[source,bash]
----
scripts/aac-host-ssh-key.sh
----

This creates `~/.ssh/aac_host_ed25519` and `~/.ssh/aac_host_ed25519.pub`. Because you are already `compliance` on the AAC host, authorize the public key directly:

[source,bash]
----
cat ~/.ssh/aac_host_ed25519.pub >> ~/.ssh/authorized_keys
chmod 600 ~/.ssh/authorized_keys
----

If you generated the key elsewhere, copy the public key to the AAC host and install it as root with `aac-host-prereq.sh --authorized-key-file <path>`.

The private key goes into `secrets.yml` in the next section.

== Secrets and variables

=== Populate the CaC variables

Edit the files under `playbooks/vars/`, replacing every `PLACEHOLDER`:

- `main.yml` — AAP connection, AAC host, your fork, PostgreSQL and Grafana usernames
- `defaults.yml` — `aac_organization`, `aap_project_default_ee` (other values are sensible defaults)
- `secrets.yml` — passwords, tokens and keys

Several values must agree with what the quadlets hard-code:

[cols="1,1,2",options="header"]
|===
| Variable | File | Must be
| `aac_host` | `main.yml` | FQDN of this AAC host
| `git_repo_url` | `main.yml` | URL of *your fork*
| `git_repo_branch` | `main.yml` | `installation-work` (the branch holding your site config)
| `pg_user` | `main.yml` | `compliance` (set by `quadlets/aac-postgresql.container`)
| `pg_db` | `main.yml` | `compliance` (set by `quadlets/aac-postgresql.container`)
| `grafana_admin_user` | `main.yml` | `admin` (set by `quadlets/aac-grafana.container`)
| `aap_project_default_ee` | `defaults.yml` | `AAC Compliance EE` after you complete <<aac-compliance-ee>> (must match the CaC object name)
| `pg_password` | `secrets.yml` | The *same value* as `compliance_db_password`
| `aac_host_ssh_private_key` | `secrets.yml` | Contents of `~/.ssh/aac_host_ed25519` as a block scalar (`aac_host_ssh_private_key: \|`)
|===

`compliance_db_password` becomes the podman secret used by the PostgreSQL container for both the `compliance` user and the `postgres` superuser; `pg_password` is what AAP uses to connect. If they differ, every database job fails to log in.

=== CAA signing key (optional, when you enable CAA on templates)

Generate the cosign key pair:

[source,bash]
----
scripts/aac-caa-signing-key.sh
----

Paste the private PEM from `ee/aac-caa-keys/cosign.key` into `playbooks/vars/secrets.yml` as `caa_signing_private_key` (block scalar). Keep `cosign.pub` for auditors.

=== Encrypt the secrets file

[source,bash]
----
ansible-vault encrypt playbooks/vars/secrets.yml
----

To change it later, use `ansible-vault edit playbooks/vars/secrets.yml`.

=== Container secrets (podman)

Create the named podman secrets (`compliance_db_password`, `grafana_admin_password`) that the quadlets use. The script decrypts `playbooks/vars/secrets.yml` and prompts for the vault password:

[source,bash]
----
scripts/aac-podman-secrets.sh
----

Use `--force` to replace existing secrets after you change a password.

== AAC containers (quadlets)

Install and start the user-level quadlets for OPA, PostgreSQL and Grafana:

[source,bash]
----
sudo scripts/aac-quadlets-setup.sh --aac-host <your-aac-host>
----

The script disables any legacy system `container-*` units, copies `quadlets/*.container` into `~/.config/containers/systemd/`, runs a Quadlet dry-run, removes hand-started containers with the same names, and starts `opa-*.service` and `aac-*.service` on the `compliance` user's systemd bus. The `aac-webserver` quadlet is skipped unless the `aac-reports-viewer:latest` image has been built with `services/build.sh`.

Verify:

[source,bash]
----
systemctl --user list-units 'opa-*.service' 'aac-*.service'
podman ps
curl -s http://<your-aac-host>:8181/health        # {}
curl -s http://<your-aac-host>:8182/health        # {}
curl -s http://<your-aac-host>:8183/health        # {}
podman exec aac-postgresql pg_isready              # accepting connections
curl -s http://<your-aac-host>:3000/api/health     # "database": "ok"
----

IMPORTANT: OPA keeps policies loaded through its API in memory only. Restarting an `opa-*.service` (or rebooting the host) empties it; re-run *AAC_Load_OPA_Policies* afterwards.

NOTE: Do not run *AAC_Deploy_OPA_Containers* on a host managed by these quadlets. That template starts root-level OPA containers with system `container-opa-*` units on the same ports, which conflicts with the rootless quadlet services.

== AAP configuration

=== Site config

The AAC playbooks read `ansible/vars/site_config.yml` from the project checkout, so it must be committed to the branch AAP syncs. Create it from the example:

[source,bash]
----
cp ../../../ansible/vars/site_config.yml.example ../../../ansible/vars/site_config.yml
vim ../../../ansible/vars/site_config.yml
----

At minimum set `aac_host` to the AAC host FQDN and review the PostgreSQL settings.

The site config is gitignored by default. In your branch, remove or comment out this line in the repository's `.gitignore`:

[source,text]
----
ansible/vars/site_config.yml
----

Then add, commit and push both files to the `installation-work` branch of your fork.

WARNING: Never open a PR from this branch: the Install Config Hygiene check fails on committed site values.

[[aac-compliance-ee]]
=== AAC Compliance execution environment

Every AAC job template runs in the execution environment named by `aap_project_default_ee` in `playbooks/vars/defaults.yml` (default: `Default Execution Environment`). That image must provide `community.postgresql` and a working `psycopg2` Python module. For a production install, build the supported EE under `ee/`, push it to a registry your controller can reach (Private Automation Hub, `registry.redhat.io`, or your own Quay organization), and seed *AAC Compliance EE* on the controller before bootstrap—not images from AAC maintainers' personal Quay accounts.

==== Build and push the image

On a RHEL 9 build host with `podman`, `ansible-builder` 3.x, and access to `registry.redhat.io` (same login as earlier on the AAC host if you build there):

[source,bash]
----
cd ee/
# Optional: CAA signing support — see "CAA signing key" above and ee/execution-environment.yml
ansible-builder build -vvv -t <registry>/<org>/aac-compliance-ee:<tag>
podman login <registry>
podman push <registry>/<org>/aac-compliance-ee:<tag>
----

Use a fully qualified image reference the controller will resolve at job time, for example `registry.example.com/aac/aac-compliance-ee:1.0.0` or `quay.io/<your-org>/aac-compliance-ee:latest`. Comments in `ee/execution-environment.yml` show the same pattern.

==== Wire the image into CaC

Before `bootstrap_controller.yml`, complete the controller execution environment definition:

. Edit `playbooks/automation_execution/infrastructure/execution_environments/aac_compliance_ee.yml` — set `image:` to your pushed reference and replace the `PLACEHOLDER` lines in the readme block with your contact metadata.
. In `playbooks/vars/defaults.yml`, set `aap_project_default_ee: AAC Compliance EE` so the AAC project and all job templates select the image you registered.

Bootstrap creates the *AAC Compliance EE* object on the controller from that file. The AAC project default and every seeded template reference `aap_project_default_ee`; they do not hard-code an image URL in the template playbooks.

==== Optional: maintainer demo execution environment

CaC also ships `aac_demo_ee.yml`, which registers *AAC Demo EE* against a public demo image (`quay.io/jumedina/aac-compliance-ee:latest`) for quick trials without building locally. A customer controller should not keep that object unless you explicitly want the demo image.

For production, remove `aac_demo_ee.yml` from the `loop` in `playbooks/automation_execution/infrastructure/execution_environments/main.yml` before bootstrap so only `aac_compliance_ee.yml` runs.

If you maintain Private Automation Hub content from this tree, `playbooks/automation_content/execution_environments/aac_demo_juan.yml` is the same demo upstream; omit it from your hub seeding playbooks. It is not invoked by `bootstrap_controller.yml`.

=== Bootstrap CaC

With `playbooks/vars/` populated and `secrets.yml` encrypted, run the controller bootstrap (`-J` prompts for the vault password):

[source,bash]
----
ansible-playbook -J playbooks/bootstrap_controller.yml
----

This creates:

- Credential Types and Credentials (attached to each job template that needs them)
- Controller Execution Environments (*AAC Compliance EE*, and *AAC Demo EE* only if you left it in `execution_environments/main.yml`)
- Projects (pointing at your fork and branch)
- Inventories and Hosts (`localhost` and `aac_host`)
- Templates and Workflows
- Schedules

NOTE: Complete <<aac-compliance-ee>> before bootstrap unless your controller's default EE already satisfies PostgreSQL job requirements and you intentionally leave `aap_project_default_ee` unchanged.

*Optional* — run the EDA bootstrap:

[source,bash]
----
ansible-playbook -J playbooks/bootstrap_eda.yml
----

This creates:

- EDA Credentials
- EDA Decision Environments
- EDA Projects
- EDA Rulebook Activations

=== Initialize the database

Run the AAP job template *AAC_Init_PostgreSQL_Database*. It creates the compliance schema and the read-only `compliance_reader` role. The *AAC Postgresql* credential supplies the `postgres` superuser password (the same `pg_password`), which the job uses once to grant `CREATEROLE` to `compliance`.

Verify:

[source,bash]
----
podman exec -it aac-postgresql psql -U compliance -d compliance -c "\dt"
----

Expect these tables:

[source,text]
----
 Schema |           Name            | Type  |   Owner
--------+---------------------------+-------+------------
 public | compliance_certifications | table | compliance
 public | compliance_facts          | table | compliance
 public | compliance_results        | table | compliance
 public | customer_frameworks       | table | compliance
 public | framework_catalog         | table | compliance
 public | host_facts                | table | compliance
 public | remediation_budgets       | table | compliance
 public | remediation_rates         | table | compliance
 public | sidecar_datasets          | table | compliance
 public | technical_debt_items      | table | compliance
 public | technical_debt_summary    | table | compliance
----

=== Seed the framework catalog

Run *AAC_Seed_Framework_Catalog*. It fills `framework_catalog` and seeds `customer_frameworks` with the frameworks marked `enabled_by_default`.

*Optional*: once managed hosts have facts in PostgreSQL, run *AAC_Enroll_Discovered_Frameworks* to enable the bundles implied by what was discovered.

=== Load REGO policies

Run *AAC_Load_OPA_Policies*. The launch survey defaults to `source=database`; choose another mode if needed. The template sets the three OPA URLs from `aac_host`.

WARNING: Without a seeded catalog, `source=database` falls back to the *baseline* set and says so in the job output.

==== Policy selection

The `source` survey answer selects which frameworks are loaded:

[cols="1,3",options="header"]
|===
| `source` | Loads
| `database` (default) | The tenant's enabled frameworks from `customer_frameworks`: the catalog baseline, plus discovery enrolment, plus the customer's own choices. Falls back to `baseline` if the catalog is not seeded.
| `baseline` | Only frameworks marked `enabled_by_default` in `ansible/vars/framework_catalog.yml`. No database needed.
| `file` | The frameworks set to `true` in `ansible/vars/policy_selection.yml`.
| `extra_vars` | Only the loader keys in the `frameworks_to_load` survey field.
| `all` | Every framework bundle. For lab and demo builds only: long run and high OPA memory.
|===

The full list of framework keys is in `ansible/vars/framework_catalog.yml`.

*file*

Copy `ansible/vars/policy_selection.yml.example` to `ansible/vars/policy_selection.yml` and set unwanted frameworks to `false`. Regenerate the example with `scripts/gen_policy_selection_example.py` when the policy library changes. Unknown keys fail the job; deselected frameworks are listed in the job output.

IMPORTANT: `policy_selection.yml` is gitignored, so AAP's project checkout will not contain it. As with the site config, remove its line from `.gitignore` in your `installation-work` branch and commit it.

*extra_vars*

For one-off loads, choose `extra_vars` and enter comma-separated loader keys in the survey, for example `cis_rhel9,iso27001`. These loads are *additive*: they never prune other frameworks.

*Reconcile* (`reconcile: true`, default)

A load prunes OPA policy IDs that are not in the set being loaded, except the AAC bridges and `exceptions_waivers`. Expect counts to drop after a narrower load; that is intentional. Setting a framework to `false` only unloads it on the next reconciling load. Two cases never prune: `extra_vars` loads, and a `database` load that fell back to baseline.

*Partial loads* (`allow_partial_load: false`, default)

The job fails if any policy file fails to load, because a partial load leaves a framework silently evaluating to `{}`. Set it to `true` only to tolerate known-bad files while troubleshooting.

==== Verify

[source,bash]
----
total_policies=0
for svc in 8181 8182 8183
do
  policies=$(curl -s http://<your-aac-host>:${svc}/v1/policies | jq '.result | length')
  total_policies=$((total_policies + policies))
  echo "Policies in OPA ${svc}: ${policies}"
done
echo "Total policies: ${total_policies}"
----

=== Grafana dashboards

With Grafana healthy on port 3000, run *AAC_Deploy_Grafana_Dashboards*. It configures the PostgreSQL datasource and imports the compliance dashboards. It does *not* start Grafana; if Grafana is down, start it with `systemctl --user start aac-grafana.service`.

IMPORTANT: `GF_SECURITY_ADMIN_PASSWORD` (from the `grafana_admin_password` podman secret) only takes effect the first time Grafana initializes its database. If you change the password later, or authentication fails, reset it with `podman exec -it aac-grafana grafana-cli admin reset-admin-password <new-password>`. A hard reset is `systemctl --user stop aac-grafana.service && podman volume rm compliance_grafanadata && podman volume create compliance_grafanadata && systemctl --user start aac-grafana.service`, followed by re-running *AAC_Deploy_Grafana_Dashboards*.
