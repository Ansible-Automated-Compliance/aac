= AAC on Existing AAP — Production-Oriented Install Guide
:toc: left
:toclevels: 3
:sectanchors:
:sectnums:

Estimated time: 2 to 4 hours for a careful first install.

== What you get

- OPA containers (`opa-security`, `opa-compliance`, `opa-ot`)
- REGO policies loaded from the `policies/` submodule
- A *dedicated* AAC PostgreSQL database
- Grafana dashboards
- An AAP project + job templates
- An Execution Environment

== Architecture recommendation

Prefer a dedicated AAC host to provide clear blast radius, capacity, and naming. Do not risk AAP data or container names. The EDA and MCP configurations are optional for a first production cut.

== Prerequisites

- AAP *2.5.5* or later
- RHEL for `aac_host`
- Outbound HTTPS to GitHub, console.redhat.com, and registry.redhat.io
- Firewall capacity for AAC ports

== AAC Host setup

=== Basic requirements

RHEL server with `compliance` user, registered to Red Hat.

If the user doesn't exist, create it:

[source,bash]
----
sudo useradd -m -c "Compliance AAC service account" -G 'wheel' -s /bin/bash compliance
sudo passwd compliance
# or
printf 'compliance' | sudo passwd compliance --stdin

echo "compliance ALL=(ALL) NOPASSWD: ALL" | sudo tee /etc/sudoers.d/compliance

echo "export TERM=xterm-256color" >> ~/.bashrc
echo "export XDG_RUNTIME_DIR=/run/user/$(id -u)" >> ~/.bashrc
echo "export DBUS_SESSION_BUS_ADDRESS="unix:path=${XDG_RUNTIME_DIR}/bus"" >> ~/.bashrc

systemctl --user daemon-reload
sudo loginctl enable-linger compliance
sudo dnf install -y podman ansible-core vim tree jq curl pip bash-completion ncurses-term
sudo dnf upgrade -y && sudo systemctl reboot
----

Switch to the compliance user:

[source,bash]
----
su - compliance
----

=== Repository checkout

Ensure your SSH key is the default to be used by git

[source,bash]
----
git config --global core.sshCommand "ssh -i ~/.ssh/id_aac_compliance"
----

From github fork the original repository https://github.com/Ansible-Automated-Compliance/aac.git

[source,bash]
----
cd ~/repos/
git clone https://github.com/Ansible-Automated-Compliance/aac.git
cd aac
git submodule update --init --recursive
tree -L 2 policies/benchmarks/

The `policies/` directory is a git submodule. After the first clone, `git submodule update --init --recursive` needs the same GitHub access (SSH key on this host, or HTTPS with credentials).

Create a branch for your local changes.

[source,bash]

Make a copy of the example secrets file and edit the PLACEHOLDERs. *Never commit real secrets*.

[source,bash]

[source,bash]

Create a classic personal access token at https://github.com/settings/tokens with the `repo` scope, store it as `vault_github_pat` in `vault_secrets.yml`, and create the *GitHub PAT (Source Control)* credential in AAP (see <<GitHub PAT credentials>> later in this guide).

compliance_reader_password: compliance
grafana_admin_password: <grafana-admin-password>

# CATEGORY 6 — CAA
caa_signing_private_key: |
  # Paste the ENTIRE contents of your cosign.key here as an indented
  # block scalar, including its BEGIN/END header and footer lines.

=== CAA signing key (required for CIS playbooks that enable CAA)

Generate keys using the cosign binary from a container.

[source,bash]
----
cid=$(podman create registry.access.redhat.com/hi/cosign:3)
podman cp "$cid":/usr/bin/cosign ./cosign
podman rm "$cid"
chmod +x ./cosign
COSIGN_PASSWORD="" ./cosign generate-key-pair
----

IMPORTANT: The *public* key is for auditors (`cosign verify-blob`); do *not* inject it as the signing secret on the template.

=== REGO policy loading

The README verify curls are *not* the load step.

Install the dependencies

[source,bash]
----
ansible-galaxy collection install amazon.aws
----

[source,bash]
----
ansible-playbook -J ansible/playbooks/load_opa_policies.yml \
  -e "opa_security_url=http://<your-aac-host>:8181" \
  -e "opa_compliance_url=http://<your-aac-host>:8182" \
  -e "opa_ot_url=http://<your-aac-host>:8183" \
  -e "source=all"
  -e "source=extra_vars" -e "frameworks_to_load=["cis_rhel9"]"
----

==== Policy Selection

By default the load_opa_policies.yml playbook will use the `source=all` option to load all policies from the `policies/` directory. If you want to load only a specific policy, you can use the options:

- `source=all` 
- `source=file` 
- `source=extra_vars` 
- `source=database` 

Using this options can reduce OPA memory, production startup time, and portal-driven enablement.

NOTE: A complete list of frameworks can be found in `ansible/vars/framework_catalog.yml`.

===== policy_selection file

Copy `ansible/vars/policy_selection.yml.example → ansible/vars/policy_selection.yml` (gitignored).

Regenerate keys with `scripts/gen_policy_selection_example.py`. 

Run the playbook with `-e source=file`. Rules: unknown keys fail; deselected frameworks are listed in job output; flipping to false does not unload until a reconcile load runs.

IMPORTANT: Because `policy_selection.yml` is gitignored, a synced project will not contain it unless someone places it on the controller’s project checkout. This is easy to miss.

===== extra_vars option

For one-off loads: `-e source=extra_vars -e 'frameworks_to_load=["cis_rhel9","iso27001"]'`.

===== database option

Depends on framework_catalog + customer_frameworks. Point to `ansible/playbooks/seed_framework_catalog.yml` and `ansible/playbooks/enroll_discovered_frameworks.yml` (“AAC - Enroll Discovered Frameworks” after gather-facts, then load with `source=database`).

===== Reconcile load

`reconcile: true` (default)

Each load prunes OPA policy IDs not in the current wanted set (except bridges + exceptions_waivers). Expect counts to drop after selective loads; that is intentional.

===== Partial Loads

`allow_partial_load: true` (default)

Default false — loader fails if any file fails. Mention for troubleshooting only if needed.

=== Grafana installation

Install Grafana

[source,bash]
----
podman volume create compliance_grafanadata
podman run -d --name aac-grafana \
  --network=host \
  --restart=always \
  -v compliance_grafanadata:/var/lib/grafana \
  -e GF_SECURITY_ADMIN_USER=admin \

TIP: `GF_SECURITY_ADMIN_PASSWORD` only takes effect on first-time initialisation against an empty database. If you re-create the container and authentication fails, delete the volume first: `podman volume rm compliance_grafanadata && podman volume create compliance_grafanadata`.

curl -s http://<your-aac-host>:3000/api/health

==== Troubleshooting Grafana

If the container becomes unresponsive, you can restart it with:

[source,bash]
----
systemctl --user restart aac-grafana.service
systemctl --user is-active aac-grafana.service
----

If needed you can disable the service with:

[source,bash]
----
systemctl --user disable aac-grafana.service
----

To force stop the service if systemctl fails, you can use:

[source,bash]
----
systemctl --user disable --now aac-grafana.service
ps aux | grep aac-grafana.service
kill -9 <process id>
systemctl --user start aac-grafana.service
systemctl --user is-active aac-grafana.service
----

To re-deploy the service, you can delete the volume and re-run the deployment playbook:

[source,bash]
----
podman volume list
podman volume rm compliance_grafanadata
podman volume create compliance_grafanadata
ansible-playbook -J ansible/playbooks/deploy_grafana_dashboard.yml \
  -e "grafana_url=http://<your-aac-host>:3000" \
  -e "pg_host=<your-aac-host>"
----

=== Quadlets

Turn off the broken system units (as root once only)

[source,bash]
----
sudo systemctl disable --now container-opa-security.service \
  container-opa-compliance.service container-opa-ot.service

sudo rm -f /etc/systemd/system/container-opa-*.service \
  /etc/systemd/system/container-aac-postgresql.service \
  /etc/systemd/system/container-aac-grafana.service

sudo systemctl daemon-reload
----

Verify the units doesn't exist

[source,bash]
----
sudo systemctl list-units | grep -E 'opa|aac'
----

As compliance — generate Quadlets for containers

[source,bash]
----
mkdir -p ~/.config/containers/systemd/
cd ~/.config/containers/systemd/
----

Copy the files in the quadlets directory to the systemd directory

Check for Syntax Errors (Dry Run)

If a .container file has a syntax error or a missing required field (like Image=), Quadlet will fail to generate the service file but will do so silently. You can manually run the Quadlet generator in debug mode to see exactly why it is rejecting your files:

[source,bash]
----
/usr/libexec/podman/quadlet -dryrun -user
----

Remove the hand-started containers so Quadlet owns them

[source,bash]
----
podman rm -f opa-security opa-compliance opa-ot aac-postgresql aac-grafana aac-webserver
----

Enable on the user bus (no sudo)

[source,bash]
----
systemctl --user daemon-reload
systemctl --user list-unit-files | grep -E 'opa|aac'
systemctl --user start \
  opa-security.service \
  opa-compliance.service \
  opa-ot.service \
  aac-postgresql.service \
  aac-grafana.service \
  aac-webserver.service
systemctl --user is-active \
  opa-security.service \
  opa-compliance.service \
  opa-ot.service \
  aac-postgresql.service \
  aac-grafana.service \
  aac-webserver.service
----

Survive logout/reboot without an interactive login

[source,bash]
----
loginctl enable-linger compliance
loginctl show-user compliance -p Linger
systemctl --user --failed
----

NOTE: Do not `systemctl --user enable` these units — Quadlet-generated units refuse it ('transient or generated'); The `[Install] WantedBy=default.target` + `loginctl enable-linger` handles boot.

=== Testing and Demonstration

==== Verify activations are running

In the AAP UI under *Automation Decisions -> Rulebook Activations*, confirm every activation shows *Running*. If an activation shows *Failed* or *Stopped*, click into it and check the *History* tab for the error. Common causes:

- *Credential mismatch* — the activation must use the `AAP Controller Token` credential, not a machine credential.
- *Port conflict* — another activation (or process) already bound to the same port. Check with `ss -tlnp | grep <port>` on the AAP host.
- *Decision Environment pull failure* — the DE image pull needs the `Red Hat Container Registry` credential attached to the DE definition. Check *Automation Decisions -> Decision Environments*.

== Native AAP Policy as Code

=== Configuration

This section wires the OPA you already run on the AAC host (`<your-aac-host>`) into *Ansible Automation Platform*'s built-in Policy as Code feature. That is separate from AAC assessment
playbooks: PAC blocks/allows *job launches* in the AAP console *before* the playbook runs.

Reference: Red Hat docs —
https://docs.redhat.com/en/documentation/red_hat_ansible_automation_platform/2.6/integrate-assembly_controller_pac

IMPORTANT: PAC evaluates *job context* (extra_vars, template, inventory, credentials, launching user). It does *not* parse playbook YAML.

==== Step 1 — Point AAP at your OPA server

In the AAP UI go to *Settings* → *Job* / *Policy settings*, Set:

[cols="2,3",options="header"]
|===
| Setting | Value for this install
| OPA Server hostname (`OPA_HOST`) | `<your-aac-host>`
| OPA server port (`OPA_PORT`) | `8181`
| OPA SSL (`OPA_SSL`) | `False` (HTTP lab)
| OPA authentication type | `None` (lab)
| OPA request timeout | `5` (seconds; default 1.5 is tight on lab links)
| OPA request retry count | `2`
|===

Save.

Verify from the AAP host:

[source,bash]
----
curl -s -o /dev/null -w '%{http_code}\n' http://<your-aac-host>:8181/health
# Expect 200
----

==== Step 2 - Create a centralized PAC policy repository

At the AAC host, create a directory for PAC policies:

[source,bash]
----
sudo mkdir -p /opt/opa/compliance/policies/pac
sudo chown -R compliance:compliance /opt/opa/compliance/policies/pac
----

==== Step 3 — Create a simple PAC Rego policy

Create a file `hello_aap_pac.rego` in the PAC policy repository:

[source,bash]
----
touch /opt/opa/compliance/policies/pac/hello_aap_pac.rego
----

[source,rego]
----
package hello.aap.pac

import rego.v1

# AAP Policy as Code contract: rule must evaluate to
# { "allowed": bool, "violations": [string] }
default result := {
	"allowed": false,
	"violations": ["hello.aap.pac: evaluation produced no decision"],
}

allowed_envs := {"development", "production"}

violations contains msg if {
	env := object.get(object.get(input, "extra_vars", {}), "environment_cli", "")
	not env in allowed_envs
	msg := sprintf(
		"PAC deny: extra_vars.environment_cli must be one of %v (got %v)",
		[allowed_envs, env],
	)
}

result := {
	"allowed": count(violations) == 0,
	"violations": [v | some v in violations],
}
----

Load it into the security OPA (package path → API path):

[source,bash]
----
curl -X PUT --data-binary @hello_aap_pac.rego \
  http://<your-aac-host>:8181/v1/policies/hello_aap_pac

# Smoke-test with empty extra_vars → deny
curl -s http://<your-aac-host>:8181/v1/data/hello/aap/pac/result \
  -H 'Content-Type: application/json' \
  -d '{"input":{"extra_vars":{}}}' | jq .

# Smoke-test with valid extra_vars → allow
curl -s http://<your-aac-host>:8181/v1/data/hello/aap/pac/result \
  -H 'Content-Type: application/json' \
  -d '{"input":{"extra_vars":{"environment_cli":"development"}}}' | jq .
----

Expect `allowed: false` then `allowed: true`.

The OPA policy name you will type in AAP is `hello.aap.pac/result`

==== Step 4 — Create the hello-aap project in AAP

Create a new project in AAP:

[source,yaml]

== Rego exceptions (security waivers)

A Rego exception is a *waiver*: a documented, time-boxed acceptance of a finding. It is not a change to the benchmark policy, and it is not an AAP Policy as Code allow rule.

The module is `policies/governance/exceptions/waivers.rego` (`package exceptions`). The entries are site data in `ansible/vars/waivers.yml`. When an assessment stores a result, `aac_store_results` asks OPA which violations an active waiver covers.

Those findings leave the active `violations` list and are stored under `metadata.waivers_applied`, with the reason, approver, and expiry attached. The score counts them as passed. An assessor still sees the exception; it is not deleted.

If OPA is unreachable or the module was never loaded, *nothing is waived*. The failure direction is always "report more".

=== Create an exception

Copy a sample from `examples/waivers_example.yml` into `ansible/vars/waivers.yml` (that file ships as `waiver_entries: []`).

Every entry needs all six fields:

[cols="1,3",options="header"]
|===
| Field | Meaning

| `host`
| Hostname as stored on the result, or `*` for every host

| `framework`
| `opa_framework_map` key (`cis_rhel9`, `cis_m365_v7`, …), or `*`

| `control_id`
| Substring matched against the violation text (`5.2.1`, `CVE-2026-12345`).
  Empty never matches.

| `reason`
| Why this is accepted, and what compensating control exists

| `approver`
| A person, not a team alias

| `expires`
| `YYYY-MM-DD`, before year 2262. No date, or a date that does not parse,
  means the entry *never waives*.
|===

[source,yaml]
----
# ansible/vars/waivers.yml
waiver_entries:
  - host: "web01.example.com"
    framework: "cis_rhel9"
    control_id: "5.2.1"
    reason: "Root SSH required by the legacy backup agent; jump-host firewall FW-118 is the compensating control"
    approver: "ciso@example.com"
    expires: "2027-03-31"
----

Matching rules:

* `host` and `framework` are exact, unless the entry uses `*`.
* `control_id` is a substring of the violation. String violations are matched as written (`CIS 5.2.1: …`). Object violations are matched against their JSON, so an id anywhere in the object is enough.
* A waiver applies only while `time.now` is *before* `expires`. After that date the same finding is an active violation again, with no edit required. The decision lists those under `expired_matches`. They are stored as `metadata.waiver_expired_matches` only when that same run also applies at least one still-active waiver.

=== Load the exceptions into OPA

`AAC - Load OPA Policies` (`ansible/playbooks/load_opa_policies.yml`) puts the module on every OPA container as policy id `exceptions_waivers`, then PUTs `waiver_entries` to `/v1/data/waivers`. Re-run the same load you used earlier in this guide after every edit of `waivers.yml`:

[source,bash]
----
ansible-playbook -J ansible/playbooks/load_opa_policies.yml \
  -e "opa_security_url=http://<your-aac-host>:8181" \
  -e "opa_compliance_url=http://<your-aac-host>:8182" \
  -e "opa_ot_url=http://<your-aac-host>:8183"
----

You can skip the file and pass entries for one run:

[source,bash]
----
ansible-playbook -J ansible/playbooks/load_opa_policies.yml \
  -e "opa_security_url=http://<your-aac-host>:8181" \
  -e "opa_compliance_url=http://<your-aac-host>:8182" \
  -e "opa_ot_url=http://<your-aac-host>:8183" \
  -e '{"waiver_entries":[{"host":"*","framework":"cis_rhel9","control_id":"1.1.6","reason":"Deferred to image CR-2201","approver":"platform-lead@example.com","expires":"2026-11-30"}]}'
----

When `waiver_entries` is already set (extra var or survey), the playbook does *not* read `ansible/vars/waivers.yml`.

Confirm the data landed (repeat for `:8182` and `:8183` if you assess against those containers):

[source,bash]
----
curl -s http://<your-aac-host>:8181/v1/data/waivers | jq .
----

Smoke-test the decision. A hit returns the finding under `waived` and omits it from `active_violations`. A miss (wrong host, expired date, control id not in the text) leaves it active.

[source,bash]
----
curl -s http://<your-aac-host>:8181/v1/data/exceptions/decision \
  -H 'Content-Type: application/json' \
  -d '{
    "input": {
      "host": "web01.example.com",
      "framework": "cis_rhel9",
      "violations": ["CIS 5.2.1: Ensure sudo is required — root login permitted"]
    }
  }' | jq .
----

Expect `waived_count: 1` and `waiver_entries_loaded` greater than 0. `waiver_entries_loaded: 0` means the data document was not loaded.

=== Use them

Loading the file does not rewrite rows already in `compliance_results`. Run the assessment again (the job template or playbook that calls `aac_store_results`). Before the INSERT, the role POSTs the hostname, framework, and violation list to:

[source,text]
----
{{ opa_security_url }}/v1/data/exceptions/decision
----

On a match it:

* stores the remaining findings in `violations`
* stores each waived finding plus its waiver entry in `metadata.waivers_applied`
* reduces `failed_controls` and raises `passed_controls` by the waived count

Waivers are on by default (`aac_waivers_enabled: true` on `aac_store_results`). Set `aac_waivers_enabled: false` on a job only when you want that run to ignore exceptions.

Read what was applied:

[source,sql]
----
SELECT hostname,
       framework,
       failed_controls,
       metadata->'waivers_applied'       AS waivers_applied,
       metadata->'waiver_expired_matches' AS expired
FROM compliance_results
WHERE metadata ? 'waivers_applied'
ORDER BY evaluation_timestamp DESC
LIMIT 10;
----

Reports that render `metadata.waivers_applied` list those lines in their own block (the M365 CIS violations report does). They are labeled as waived, not omitted. A waiver whose `expires` date has passed does not appear there; the finding is an active violation again.

== Procedure to update a branch from another branch retaining modifications

=== Procedure to update the main branch if forked from another repo

Set the credential helper to cache the credentials for 1 hour (default is 15 minutes):

[source,shell]
----
git config --global credential.helper 'cache --timeout=3600'
----

Unset the credential helper:

[source,shell]
----
git config --global --unset credential.helper
----

Verify your upstream is pointing to the fork

[source,shell]
----
git remote -v
----

If the upstream is not already set, add it

[source,shell]
----
git remote add upstream https://github.com/Ansible-Automated-Compliance/aac.git
----

Fetch the latest modifications and merge them to your main branch

[source,shell]
----
git fetch upstream
git checkout main
git pull origin main
git merge upstream/main
git submodule update --init
git push origin main
----

NOTE: When creating GitHub PAT ensure you select the `repo` scope and `workflow` scope.

[WARNING]
====
This deletes every local commit in main branch and overwrites with the upstream main branch. Use only if you are sure you want to discard all local changes.

[source,shell]
----
git reset --hard upstream/main
git push origin main --force
----
====

=== Procedure to update a secondary branch from the main branch retaining modifications

. Commit first

[source,shell]
----
git add .
git commit -m "local edits"
git branch backup-before-sync
git fetch origin
----

Checkout to the branch where you want to perform the merge

[source,shell]
----
git fetch origin
git checkout <branch-name>
git merge origin/main
git submodule update --init
----

// . Backup your recent changes in the branch
// +
// [source,shell]
// ----
// git diff --name-only main | grep -vE "docs|scripts|integrations|py|^\.|md"

Save your version and the patch of what you changed since this branch diverged from main. Keep both under your home directory so a later git add . cannot commit them:

[source,shell]
----
mkdir -p "$HOME/tmp/branch-backup"
git show HEAD:path/to/file > "$HOME/tmp/branch-backup/file"
git diff "$(git merge-base HEAD origin/main)" HEAD -- path/to/file \
  > "$HOME/tmp/branch-backup/file.patch"
----

Push the changes to the remote branch

[source,shell]
----
git push origin active-branch
----
