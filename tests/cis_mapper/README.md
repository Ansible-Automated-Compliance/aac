# CIS Linux mapper unit harness

Renders `ansible/tasks/cis_linux_build_opa_input.yml` with Ansible's own
templating engine (no playbook run, no hosts) against a fact fixture in the
shape the shared collector produces, then evaluates the result against the
Rego library. This is how "the playbook really sends what the policy reads"
is proven without an AAP job.

```bash
PY=$(head -1 "$(command -v ansible-playbook)" | sed 's/^#!//')   # the interpreter that has ansible
$PY tests/cis_mapper/render_mapper.py ansible/tasks/cis_linux_build_opa_input.yml \
    tests/cis_mapper/fixtures/rhel9_facts.fixture.json /tmp/opa_input.json
opa eval -f pretty -d policies/benchmarks/cis/rhel_9/ -i /tmp/opa_input.json \
    'object.filter(data.cis_rhel9.main.compliance_report, {"assessment_coverage_percentage","sections_not_assessed","total_controls","passed_controls","failed_controls"})'
```

Expected with the shipped fixture (2026-10-22, policies at rego `dd688ae3`, CIS
RHEL 9 v3.0.0), per `profile`:

| profile | total | passed | failed | evidence missing |
|---|---|---|---|---|
| level1_server | 263 | 232 | 31 | 1 |
| level2_server | 352 | 271 | 81 | 1 |
| level1_workstation | 252 | 221 | 31 | 1 |
| level2_workstation | 341 | 260 | 81 | 1 |

The one evidence-missing id is 2.4.1.7: the fixture host has no
`/etc/cron.yearly`, and the library reads only its mode (an absent directory
is not handled there yet). A stock RHEL 9.8 cronie install has none either
(lab run 2026-10-22); the mapper reports `cron.cron_yearly_exists: false`.
6.2.3.36 fails on the fixture because `augenrules --check` prints the path it
was invoked by (`/sbin/augenrules: No change` on RHEL 9.8) and the library
matches only `/usr/sbin`. The failures are genuine for
the synthetic host (attestations not given, `overlay` loaded, ptrace_scope not
persisted, audit rules and PAM settings below the benchmark, ...); they are
kept on purpose so the fixture is not tailored to pass.

The fixture lives under `fixtures/` with a `.fixture.json` suffix because the
repository ignores `*_facts.json`. It is synthetic (RFC 5737 address,
example.com names, no lab identifiers) and is regenerated by hand: edit the
JSON, keeping each supplement block's last line `end:ok`.

Besides rendering, the harness asserts that hostile strings in the supplement
blocks (user names, certificate subjects, key comments) are not evaluated, that
a supplement section is not emitted without its collector block's `end:ok`
marker, and that supplement fields extend (recursive combine) rather than
replace the base pam / auditd / cron sections.
It also asserts evidence integrity: a block whose `end:ok` is duplicated or not
its last line (a forged line), or a fixed-path stat or sysctl key reported twice,
is not collected, so the policy reports NOT ASSESSED / evidence missing rather
than reading a forged value as a pass. A hostile host name (a `|` or control
character, which any user can put in a file name) is printed by the collector as
`unsafe:<sha256 prefix>` with its record intact: the harness checks that such a
world-writable dotfile still reaches the policy and that the block stays valid.

`collector_shell_test.sh` runs the collector's supplement blocks themselves
in a UBI 9 container (podman, `registry.access.redhat.com/ubi9/ubi`) against
hostile host states and asserts that none of them yields a pass:
- a missing `ssh-keygen`
- an `authorized_keys` whose first line is not a key (this must not hide a
  1024-bit RSA key after it)
- a symlinked `authorized_keys` (never read; the link's own 0777 mode is the record)
- more world-writable dotfiles than the cap (`truncated|dotww`)
- a file name containing a newline and a forged `end:ok`
- a user crontab mentioning aide (this does not count)
- a certificate that cannot be parsed (recorded, not skipped)
- a non-root-owned, and a group-writable, `/etc/cron.d` schedule naming aide
  (neither counts)
- only one of the two AIDE database file names present (`aide_db|yes`)
- root's own home with a world-writable dotfile (root is scanned like any
  interactive account)
- the usr-merge `/bin` symlink on root's PATH (judged by its target, not the
  0777 link)
- a missing `/etc/shadow` (`truncated|shadow`: the block is rejected, never an
  empty passing list)
- a host without `find` (the certificate block names it and never prints `end:ok`)

```bash
tests/cis_mapper/collector_shell_test.sh "$PY"
```

The v3 blocks (2026-10-21: `kmod_raw`, `sysctl_raw`, `pkg_state_raw`,
`config_raw`, `perms_raw`, `accounts_raw`, `fs_sweep_raw`) are covered by the
same checks: each needs its own unique, last `end:ok`; duplicate singletons,
missing commands and truncation are "not collected" (a capped /var/log,
GRUB, unowned / ungrouped / non-sticky / privileged list drops only that
field); a kernel parameter persisted nowhere is `unset` (a fail, not missing
evidence); package booleans are emitted only from the RPM database; a
systemctl unit record never overrides a service_facts one; hostile text in
the configuration lines stays verbatim; shadow evidence is password state
and aging only. `collector_shell_test.sh` adds: no module tree for the
running kernel (`truncated|modules_dir`), a newline-and-forged-`end:ok` log
file name, no local filesystem to sweep (every list truncated) and a root
password hash that must not leave the block.

## Ansible argument check

`check_task_args.py` runs Ansible's own free-form argument splitter over every
`shell`/`command` task. An odd apostrophe in a shell comment ("user's") makes
the task fail at run time with "unbalanced jinja2 block or quotes", which the
shell test and the mapper harness above do not exercise (found on the first
real-host run, 2026-10-19).

```bash
$PY tests/cis_mapper/check_task_args.py ansible/tasks/collect_linux_compliance_facts.yml
```
