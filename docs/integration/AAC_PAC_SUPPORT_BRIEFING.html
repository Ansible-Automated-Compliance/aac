What is AAC?
AAC = Policy-as-Code (PaC) + three OPA servers + a database + the policy library. While PaC keeps your automation in policy, AAC extends that protection—maintaining historical compliance records, standardizing compliance libraries, and establishing governance that proves infrastructure posture.

The Problems AAC Solves
SLIDE 03
Legacy / Industry Challenge AAC Solution
Manual, Expensive Audits: Audit evidence relies on screenshots, spreadsheets, and interviews repeated every cycle. Durable Records: Every assessment produces a durable, scored, cosign-signed record verifiable offline.
Tool Silos per Framework: CIS, STIG, NIST, ISO 27001, PCI-DSS, SOX, NERC-CIP, and IEC 62443 are operated separately. Unified Engine: 50+ frameworks supported on one engine, using one language and one evidence store.
Unmonitored Drift: Nothing watches systems between audit cycles; unauthorized changes surface months later. Continuous Baselining: Baselines configurations, detects unauthorized change, and tracks trend history.
Ungoverned Automation: Playbooks, Terraform plans, container images, and AI changes reach production unchecked. Multi-Gate Enforcement: Gates changes at git check-in, runtime, and audit sweep.
Platform Native: All capabilities execute natively on the platform customers already run: Ansible Automation Platform (AAP).
What Policy-as-Code (PaC) Is
SLIDE 04

Supported Red Hat Product Feature: Generally Available (GA) in AAP 2.5.5; fully documented in AAP 2.5, 2.6, and 2.7.

Architecture & Mechanics

  • AAP + OPA Integration: The AAP Controller invokes an external Open Policy Agent (OPA) server to evaluate Rego policy before a job launches.
  • UI-Configured Settings: Managed via first-class Controller settings (OPA_HOST, OPA_PORT, TLS/auth, 1.5s timeout, 2 retries).
  • Flexible Scope: Policies are associated at the Organization, Inventory, or Job Template level.
Customer Responsibility: Under standard PaC, the customer provides the OPA server infrastructure and writes the Rego policies (Red Hat supplies 12 example policies).
How PaC Works (Execution Path)
SLIDE 05
User launches job
      │
      ▼
AAP Controller builds job-context JSON
      │
      ▼
OPA evaluates policy ───► POST /v1/data/<policy> [1.5s timeout]
      │
      ▼
Returns Decision ───────► { "allowed": false, "violations": ["..."] }
      │
      ├─► allowed     ──► Job runs
      └─► not allowed ──► Job blocked

Key Operational Characteristics

  • Synchronous Launch Gate: Executes directly on the launch path; delivers a policy decision in under 2 seconds.
  • Metadata Inspection Only: Input is limited to job metadata; PaC never sees playbook contents.
  • Stateless Execution: Nothing is persisted; the decision gates the launch and is discarded.
What AAC Is
SLIDE 06
Formula: AAC = PaC + 3 Domain OPA Instances + PostgreSQL Evidence DB.
Uses the same engine, same language (Rego), and same API as PaC, while adding historical persistence and pre-built content.

Core Extensions

  • Three Domain-Split OPA Servers:
    • opa-security: CIS, NIST, STIG
    • opa-compliance: ISO 27001, SOC 2, PCI-DSS, SOX, FISMA, Digital Sovereignty
    • opa-ot: NERC-CIP, AMI, IEC 62443
  • Playbook-Level Fact Evaluation: AAP jobs collect system facts (~180 KB/system) and POST evaluations to /v1/data/<framework>/compliance_report.
  • Persistent Historical Evidence: Stores every evaluation as a durable, timestamped, scored PostgreSQL row, cosign-signed for offline audit verification.
  • Pre-Built Policy Library: Includes 550+ curated policy files across ~24 framework families (compared to PaC's blank page).

Key Operational Characteristics

  • Asynchronous Assessment: Operates off the launch path; takes seconds to minutes per framework.
  • Full Persistence: Stores long-term trends, quarter-over-quarter posture, and a complete chain of evidence.

Triage Flow Boundary

Standard Support (Layers 1–3): AAP health → EE configuration → OPA network reachability.
Content Domain (Layers 4–7): Policies loaded → Framework resolution → PostgreSQL schema → Output accuracy.

Covering the Rest: The Galaxy Tiering Model
SLIDE 11

Rego policy libraries follow the established Ansible Collections (Galaxy) model:

Tier Hosting Location Support Level Current AAC Status
Community Ansible Galaxy / Git Community-supported (No SLA / No Entitlement) Current State (Public, Apache-2.0)
Validated Automation Hub Red Hat tested against matrix Target Next Rung
Certified Automation Hub Full Red Hat Product Support with SLAs Long-term Target

Requirements to Advance Above Community Tier

  • Technical Standards: Bounded scope, Semantic Versioning (SemVer), signed releases, automated CI testing, and diagnostic bundle generation.
  • Organizational Ownership: Named owning team with a defined defect SLA, lifecycle policy, CVE response plan, and license reconciliation.
The Maintenance Treadmill: Compliance frameworks churn continuously (CIS benchmarks update, NERC reissues standards). Whoever owns a tier above Community owns the maintenance treadmill.
Path Forward & Action Items
SLIDE 12

Component Maturity Analysis

  • Policy Library (550+ Policies): Product-grade maturity; 540+ automated tests gated in CI. Ready for Validated tiering.
  • Delivery Layer: Currently a reference implementation (9 tests, no CI). Should remain explicitly out-of-scope for product support (Customer/Consulting-owned).
The Core Question for Support Leadership:
Not “Can AAC be supported?”, but rather “Which tier does each content component belong in, and what is the required bar to advance it to the next tier?”
